## 3. 硬件接线与串口问题的解决过程

最终串口分配：

```text
电脑 COM7 ↔ 板载 CH340 ↔ F407 USART1（PA9/PA10）：调试日志
F407 USART3（PB10/PB11）↔ ESP32-C3 UART1（GPIO6/GPIO7）：AT 命令
ESP32-C3 USB/COM8：下载与启动日志，不是本工程的 AT 通道
```

实际连线：PB10（USART3_TX）→ ESP32-C3 GPIO6/IO6（UART1_RX），PB11（USART3_RX）← GPIO7/IO7（UART1_TX），两板 GND 共地。ESP32-C3 GPIO20/21 所在 UART0 为日志口，不接 F407 的 AT 通道。

早期把 ESP32 与板载 CH340 同时接到 F407 USART1，导致串口争用，表现为 AT 无响应、时间查询失败或反复发送。改用独立的 USART3 后，以串口透传工程确认 COM7 发送 `AT` 返回 `OK`、`AT+GMR` 返回固件版本。此排障结论是后续修改串口时的首要约束：**USART1 只给电脑调试，ESP-AT 只走 USART3**。

若 ESP32-C3 日志显示 `DOWNLOAD(USB/UART0/1)` 与 `waiting for download`，它仍处于下载模式，需要检查 BOOT/复位状态；这不是 AT 固件正常运行状态。

## 4. 裸机功能的实现顺序

### 4.1 页面与资源

先在 NT35510 上复现三张卡片和初始化占位。`NT35510_GramScan(0)` 使用纵向坐标，原点在左上角。当前卡片分别为：顶部 `(16,16,448,270)`、室内 `(16,306,448,225)`、天气 `(16,551,448,225)`。背景 RGB565 为 `0xD73E`，卡片白色。

主页面在数据到来前显示 `--:--`、`----/--/--`、室内和室外温湿度占位、空天气图标框。天气城市标题是 **上海市**；此前“杨浦区”的文字和 API 地点都已改掉。右上角 Wi-Fi 名称来自 `AT+CWSTATE?` 的 SSID；启动时连接失败显示 `-----`。为避免越界，长 ASCII SSID 会缩小字号，超过显示长度会以 `...` 截断。

中文字库源文件位于 `resource/font/`，对应 `User/font/weather_font_data.c`。两套字模分别是 **24×20、每字 60 字节**和 **24×24、每字 72 字节**，当前索引总数为 49，以 `User/font/weather_font.h` 和 `resource/font/*_index.TXT` 为准。先前发生的汉字破碎、错位，根因是资源更换后仍使用旧索引，以及把 20 号字模当成 24×24 来读取。重做字库时须同时核对索引、单字字节数和绘制尺寸。

图标原件在 `resource/image/jpg/`，Image2LCD C 数组在 `resource/image/c/`。原始数组通常包含 8 字节元数据；RGB565 像素为**低字节在前**。`NT35510_DrawImageScaled()` 以 `((uint16_t)pixel[1] << 8) | pixel[0]` 还原颜色，并在 `NT35510_OpenWindow()` 后发送 `CMD_SetPixel`。新加入的 17 张天气图标由 `F407_WeatherClock/tools/convert_weather_icons.ps1` 缩到 110×110，生成于 `User/image/weather/`；这些生成数组**只有像素，没有 8 字节头**，以控制 1 MB Flash 用量。

### 4.2 启动时检查 Wi-Fi

`ClockApp_Run()` 初始化 LCD、SysTick、调试串口和 ESP-AT；启动页先显示“FreeRTOS智能天气时钟”和“WIFI连接中...”。程序使用 `AT+CWSTATE?` 查询 Wi-Fi 状态，状态码 `2` 表示已连接，并从同一响应提取 SSID；最长等待约 15 秒。成功显示“连接成功！”，失败显示“连接失败！”，结果停留 3 秒后进入主页面。

启动连接失败时，主页面 Wi-Fi 名称为 `-----`，时间和室外天气保持占位；DHT11 室内数据仍会正常尝试更新。进入主页面后约每 5 秒再次查询 Wi-Fi，连续两次查询失败才判定断线，避免单次串口超时导致界面误变。断线后右上角改为 `-----`，室外天气清回占位；**若网络时间此前已同步成功，F407 RTC 继续走时并刷新屏幕时间**。重新连接后更新 SSID、重新配置 SNTP、重新校时并获取天气。Wi-Fi 检查与天气 HTTP 请求共用裸机主循环，遇到阻塞请求时，实际断线显示可能晚于两个 5 秒周期。

### 4.3 网络校时与本地 RTC

连接成功后配置 ESP-AT SNTP：

```text
AT+CIPSNTPCFG=1,8,"ntp1.aliyun.com","ntp2.aliyun.com"
AT+CIPSNTPTIME?
```

ESP 返回的时间已经是配置的 UTC+8 本地时间，**F407 解析后直接设置 RTC，不再额外加 8 小时**。请求结果必须是有效年月日；`1970/01/01` 表示尚未同步，之后按约 10 秒间隔重试。成功后将网络时间写入 F407 RTC，主循环每 200 ms 读取 RTC；秒值改变才重绘时间、日期和星期，屏幕时间只显示到分钟。

RTC 由 `User/rtc/weather_rtc.c` 管理：优先 LSE 32.768 kHz，失败则用 LSI；备份标记 `0xA55A` 防止每次复位重置日历，默认初值为 2026/09/18 22:30:00。即使 RTC 保存了旧时间，当前界面仍按产品要求，在启动 Wi-Fi 失败时保留时间占位。

### 4.4 室内与室外天气

DHT11 接开发板 J5：3.3 V、PE3 数据线、GND；板上有 10 kΩ 上拉。驱动用 DWT 做微秒时序，每 2 秒读取一次，校验成功才覆盖室内温湿度占位，失败时保留已有显示。

室外天气来自 ESP-AT 的 HTTPS `AT+HTTPCLIENT` 请求：心知天气 `weather/now.json` 读取当前温度和天气代码，`weather/daily.json` 读取当日最高/最低温度。查询地点使用 `shanghai`、语言使用 `en`；曾尝试杨浦区，但当前 API 权限不能访问该地点，而上海市可返回数据。密钥配置在 `User/esp_at/esp_at.c`，**交接文档不记录密钥值**。

网络时间查询已尝试后，天气约每 60 秒请求一次；两项天气请求均成功才刷新天气卡片。天气代码由 `User/page/main_page.c` 映射到图标与中文文字，覆盖晴、多云、阴、阵雨、雷阵雨、各级雨雪、雨夹雪、沙尘、雾、霾和风等代码 `0–36`。没有专用素材的冻雨代码 `19` 暂用普通雨图标与“雨”，`37/38/99` 等无对应素材时显示占位。刷新前先清除天气图标、温度和整条天气文字区域，以免旧文字残留。

## 7. FreeRTOS 内核接入：最小节拍测试工程

独立工程：`D:\STM32\天气时钟代码复现\F407_WeatherClock_FreeRTOS`。从裸机工程复制驱动和 Keil 配置，参考 `WeatherClock-main/third_lib/freertos` 移入 FreeRTOS V10.4.3 LTS Patch 3 的 `tasks.c`、`queue.c`、`list.c`、`timers.c`、`heap_4.c` 和 Cortex-M4F `port.c`。配置 1 ms tick、32 KiB RTOS 堆；保留硬件 FPU 设置。

此阶段的 `User/main.c` **只运行 USART1 串口节拍任务**，不启动天气时钟页面、Wi-Fi 或 ESP-AT。应在 COM7、115200 8-N-1 看到一次 `[RTOS] scheduler starting`，此后约每秒看到 `[RTOS] tick=... ms`，数值约增加 1000。输出文件名为 `RTOS_Smoke.hex`，避免与裸机 `Template.hex` 混淆。

FreeRTOS 的 `port.c` 接管 SVC、PendSV 和 SysTick；`vApplicationTickHook()` 继续更新 `g_system_ms`，供后续 ESP-AT 迁移使用。不能恢复旧的 `User/stm32f4xx_it.c` 中同名空处理函数，否则会与内核中断入口冲突。

已静态核对 Keil 工程列出的 69 个文件路径全部存在，FreeRTOS 源文件为 6 个。当前环境未找到 ARMCC/ARMClang 工具链，**尚未编译或烧录此 FreeRTOS 测试固件**；下一验收点是在 Keil 编译并上板确认串口节拍稳定，再迁移启动页和业务任务。

2026-09-23 用户提供上板串口截图：`tick` 从 4004、5005、6006 依次增长，约每秒增加 1001 ms，最小调度测试通过。工程随后进入启动任务阶段：高优先级 `init` 任务负责 LCD 初始化、启动页、最长 15 秒 Wi-Fi 查询、3 秒结果显示以及切换主页面；低优先级监视任务每 5 秒打印一次 tick。等待期间使用 `vTaskDelay()` 释放 CPU，没有再次配置 SysTick。输出文件改为 `RTOS_Startup.hex`。此阶段暂不启动时间、天气或 DHT11 周期更新，需单独上板验证启动成功和失败两条路径。

用户随后确认启动任务两条路径均通过：有 Wi-Fi 时启动页显示连接成功，主页面右上角显示 SSID；无 Wi-Fi 时等待约 15 秒显示连接失败，主页面显示 `-----`。

下一阶段仅加入 `time` 任务。启动连接成功后，`init` 任务创建 `time` 任务并自删除；该任务通过 USART3 请求 SNTP 时间，写入 F407 RTC，失败时每 10 秒重试，成功后从 RTC 刷新页面。启动连接失败时不创建时间任务，时间保持占位。为避免多个任务的 `printf` 交错，已移除完成使命的 tick 监视任务。天气、DHT11 和运行中 Wi-Fi 恢复仍未启用。输出文件为 `RTOS_Time.hex`。

时间任务上板后时间和日期正确，但 2026-09-23（星期三）显示为星期四。原因是 ESP 英文星期曾按 `Sun=1 ... Sat=7` 转换，而 STM32 RTC 常量采用 `Mon=1 ... Sun=7`。现已将 SNTP 星期转换调整为 STM32 顺序，并同步修复裸机与 FreeRTOS 工程；2026-09-23 的 `Wed` 现在写入 RTC 值 3，对应页面“星期三”。

用户重新上板确认时间、日期和星期均正确，时间任务阶段通过。下一阶段参考原工程 `ui.c` 的单一显示任务结构，新增 `clock_ui.c/.h`：时间任务不再直接操作 LCD，而是把时间结构体复制进 UI 队列，由 `ui` 任务统一刷新。随后新增 `indoor` 任务，每 2 秒读取一次 DHT11 并向同一队列发送温湿度。DHT11 的单总线脉宽对任务切换敏感，读取期间约 20 ms 暂停任务调度但保持中断开启，读取结束后才发送 UI 消息。输出文件为 `RTOS_Indoor.hex`；天气和运行中 Wi-Fi 恢复尚未启用。

### 8.1 工程入口与任务边界

当前仓库中的正式工程为：

- 裸机版：`bare-metal/Project/RVMDK（uv5）/BH-F407.uvprojx`
- FreeRTOS 版：`freertos/Project/RVMDK（uv5）/BH-F407.uvprojx`

FreeRTOS 版已经删除未使用的单循环应用路径。启动任务完成显示和应用状态初始化、创建工作任务后自删除；主页面立即显示，Wi-Fi 在后台连接。运行时职责如下：

- `ui` 任务独占 LCD。其他任务把最新状态写入邮箱，再用长度为 1 的唤醒队列通知 UI；UI 只重绘发生变化的字段。
- `time` 任务负责 RTC 初始化、读取和时间显示。RTC 初始化状态与时间可信状态分开保存。
- `indoor` 任务每 2 秒读取 DHT11。读取期间短暂暂停任务调度，但中断保持开启。
- `network` 任务独占 ESP-AT 命令通道，负责 Wi-Fi 状态、SNTP、实时天气和预报请求。

USART1 PA9/PA10 是 115200 8-N-1 电脑调试串口；USART3 PB10/PB11 是 ESP32-C3 ESP-AT 专用通道。不要让其他任务或模块直接向 USART3 发送 AT 命令。

### 8.2 当前显示与恢复规则

- 上电后直接进入主页面。有效的备份 RTC 时间可立即显示；从未取得可信时间或 RTC 不可用时显示时间占位。
- Wi-Fi 连接成功后右上角显示当前 SSID；未连接或运行中断线时显示 `-----`。
- 联网后通过 SNTP 校时，正式配置为每小时再次校时。写 RTC 失败后先尝试回滚：回滚成功则恢复原时间和有效标记；回滚也失败则清除时间有效标记，界面改为时间占位。
- RTC 初始化失败时每 60 秒重试。网络连接和天气请求继续运行；在 RTC 可用前暂缓网络时间写入。
- 实时天气和当天最高／最低温度分别请求、分别提交。任一请求失败时保留对应的上一次有效数据。
- 运行中断网后保留最后一次成功天气，并显示 `HH:MM更新`。实时天气和预报都重新获取成功后隐藏该提示。
- 天气温度使用有符号整数并检查格式与范围，零下温度不会被转换成错误的正数。
- ESP 响应可区分 AT 错误、超时、响应缓冲区溢出和接收队列溢出，相关计数会输出到调试串口。
