# 测试方法、结果与验证边界

这里区分电脑上的纯 C 测试、开发板功能测试和长期运行指标，避免把一次观察写成保证值。历史过程和故障注入结果见 [交接记录第 8 节](界面复现交接文档.md#8-当前最终状态更新至-2026-09-25)。

## 主机测试

执行 `sh freertos/tests/run_tests.sh`，或使用 [测试 README](../freertos/tests/README.md) 的手工编译方式。两组测试曾在 Windows MSVC 严格警告模式通过，并由 [主机测试 PR #13](https://github.com/Gloriamt/STM32F407-WeatherClock/pull/13) 的 GitHub Actions 验证通过。

| 测试模块 | 覆盖内容 | 判断标准 |
| --- | --- | --- |
| `weather_parser_test` | 正／负温度、范围边界、缺字段、非法数字、截断数值、API 错误回复、空指针 | 合法值正确返回；失败时不覆盖原有温度或预报 |
| `at_response_test` | CRLF 包围的 OK/ERROR、文本内的终止符单词、不完整／错误终止符、缓冲溢出、空和零容量捕获 | 正确识别命令终止；溢出仍能捕获尾部终止符 |

上述天气解析测试覆盖目标数值字段，不代表实现了完整 JSON 结构、HTTP 状态或所有服务响应的校验。AT 捕获测试也不模拟 USART、FreeRTOS 队列时序或网络服务。

## 上板功能与故障用例

| 场景 | 已执行方式 | 已确认结果 |
| --- | --- | --- |
| 正常启动 | 连接热点后复位，检查页面和日志 | SSID、时间日期星期、温湿度及天气显示正常 |
| 无网启动 | 关闭热点再启动；分别验证有效／无效 RTC 状态 | 主页面后台联网；有效 RTC 继续走时，首次未校时时占位 |
| 实时天气单项失败 | 临时让实时请求失败、保留预报请求 | 预报继续更新，实时数据保留旧值 |
| 预报单项失败 | 临时让预报请求失败、保留实时请求 | 实时天气继续更新，预报保留旧值 |
| 运行中断网／重连 | 关闭热点，等待检测，再开启热点 | SSID 变化、天气保留、离线更新时间提示、重连刷新恢复 |
| 周期校时 | 临时把校时间隔改为 60 秒，观察第二次 RTC 更新 | 调度路径和重复校时可用；正式配置恢复 1 小时 |
| RTC 初始化失败 | 临时故障注入，然后撤销并回归 | 每 60 秒重试；天气／Wi-Fi 继续，RTC 不可用时暂缓校时查询 |
| RTC 写入失败 | 临时故障注入，验证回滚成功后离线重启 | 原时间和有效标记恢复，保存时间可继续显示 |

故障注入仅用于当时验证，正式固件中未保留测试开关。相关记录：[天气部分失败 #2](https://github.com/Gloriamt/STM32F407-WeatherClock/pull/2)、[校时与回滚 #5](https://github.com/Gloriamt/STM32F407-WeatherClock/pull/5)、[离线天气 #6](https://github.com/Gloriamt/STM32F407-WeatherClock/pull/6)、[RTC 状态与初始化失败 #9](https://github.com/Gloriamt/STM32F407-WeatherClock/pull/9)。

## 24 小时运行记录

测试于 2026-09-25 完成，硬件为野火 STM32F407 霸天虎 V2、4.3 寸 NT35510、DHT11 和 ESP32-C3 ESP-AT v4.1.1.0；FreeRTOS V10.4.3 LTS Patch 3，堆配置为 32 KiB。开发板持续运行，USART1 输出 `[METRICS]`；用户确认页面、时间、室内采集、天气和 Wi-Fi 功能正常。

| 指标 | 结束时的记录 |
| --- | ---: |
| UI／时间／网络／室内最小剩余任务栈 | 934／445／657／478 words |
| 当前／历史最小剩余堆 | 17000／12776 bytes |
| ESP 响应溢出／RX 溢出／丢字节／解析错误 | 0／0／0／0 |
| UI／DHT 最大操作耗时 | 32／24 ms |
| 实时天气／预报最大请求尝试耗时 | 8011／4850 ms |

记录见 [运行指标 #10](https://github.com/Gloriamt/STM32F407-WeatherClock/pull/10)、[堆余量 #12](https://github.com/Gloriamt/STM32F407-WeatherClock/pull/12) 和 [24 小时验证 #14](https://github.com/Gloriamt/STM32F407-WeatherClock/pull/14)。

指标解释：

- 栈记录单位是 FreeRTOS stack words，堆单位为 bytes。堆最小余量与初始短期测试一致，只能说明本轮未观察到继续下降，不能证明所有运行场景不存在泄漏。
- UI 和 DHT 指标是所测操作的墙钟耗时，包含可能的调度／中断影响，不是 CPU 使用率或完整实时性分析。
- 天气耗时统计成功和失败的尝试。最长 `8011 ms` 接近 `8000 ms` 超时配置，无法根据这个数字判断对应请求结果。接收诊断为零也不等于没有 AT 错误或超时；未记录按请求类别划分的成功率。
- 结束时与手机秒级比较约慢 3 秒。这是一个时刻的差值，不是 24 小时累计漂移或高精度校准结果。
- 24 小时功能观察没有附带完整、带时间戳的校时日志，因此不以它证明正式 1 小时校时周期；已有直接证据来自 60 秒临时间隔测试。

## 后续复测建议

1. 对正式固件保持连续联网超过 1 小时，串口助手启用保存日志及时间戳，记录相邻 `[SNTP] RTC updated`。
2. 记录启动、运行中及结束的堆／栈指标；检查非人为复位是否再次出现 `[RTOS] scheduler starting`。
3. 暂时断网，再连接，观察 `[WIFI]`、`[RTC]`、天气保留与更新提示。网络恢复由 ESP 的自动连接配置和应用状态检测共同完成。
4. 若进一步验证双重 RTC 写入／回滚失败，在单独测试分支注入故障，确认清除时间有效标记并显示占位；完成后移除注入代码并回归。
5. 若需要请求成功率，单独增加实时天气和预报的成功、AT 错误、超时次数，避免用“最长耗时”代替请求结果。

本轮无溢出记录不足以证明其他流量下也没有瓶颈，因此继续保留当前 1024 字节字节队列。只有测量出现丢字节或延迟问题时，再评估环形缓冲区、DMA 或其他驱动调整。
